# CONTRACT — Reading List Tracker

Single source of truth for every agent. Read this before writing any code.
If your prompt and this file disagree, this file wins — stop and tell the human.

---

## 1. Stack
- Backend: Python + FastAPI
- Tests: pytest + FastAPI TestClient
- Frontend: plain HTML / CSS / JavaScript (no framework, no build step)
- Storage: in-memory (data resets when the server restarts — acceptable for this demo)
- Hosting: Render (free tier)
- Render currently runs the app natively (no Docker): build `pip install -r backend/requirements.txt`, start `cd backend && uvicorn app.main:app --host 0.0.0.0 --port $PORT`, health check `/health`.
- One Render service: FastAPI serves the API under `/api` and the frontend page at `/`. Same origin, so no CORS. The frontend uses relative URLs (`/api/books`).

## 2. Book
| Field | Type | Rules |
|---|---|---|
| id | integer | generated by the store: 1, 2, 3… |
| title | string | required, trimmed, cannot be empty or only spaces |
| author | string | optional, trimmed, defaults to `""` |
| status | string | required, must be one of `to-read`, `reading`, `done` · no default: missing status is a validation error |

Titles and authors are stored exactly as the user typed them (only trimmed).
There is no duplicate check: adding the same book twice creates two books.

## 3. Endpoints
| Method | Path | Success | Errors | Owner |
|---|---|---|---|---|
| POST | `/api/books` | 201 + the created Book | 400 missing/blank title · 400 missing or invalid status | Add-book |
| PATCH | `/api/books/{id}` | 200 + the updated Book | 400 missing or invalid status · 404 unknown id | Add-book |
| GET | `/api/books` | 200 + list of Books, in the order they were added | — | List/filter |
| GET | `/api/books?status=X` | 200 + only Books with that status | 400 if X is not one of the 3 statuses | List/filter |
| GET | `/api/books/stats` | 200 + `{ "to-read": n, "reading": n, "done": n }` — all 3 keys always present, zeros included | — | List/filter |
| GET | `/health` | 200 + `{ "ok": true }` | — | Lead (skeleton) |

- PATCH changes **status only** (the email asks only to change a book's status). Any other fields in the body are ignored.
- **Every error** uses the same body: `{ "error": "<readable message of what is wrong>", "status": <same number as the HTTP code> }`
  - e.g. `400 { "error": "Title is required", "status": 400 }`
  - e.g. `404 { "error": "Book 7 not found", "status": 404 }`
- FastAPI's default 422 validation response must be converted to this 400 shape (an exception handler in `main.py`, built by the lead in the skeleton).
- To return an error from a route, raise `HTTPException(status_code=..., detail="readable message")`. The handler in `main.py` turns it into the error body above. Do not build error JSON by hand.
- The frontend shows `error` in its success/error popup.
- The `/api/books/stats` route must not be captured by `/api/books/{id}`.

## 7. Rules about this contract
- `CONTRACT.md` is the single source of truth. If your prompt disagrees with it, the contract wins: follow the contract and report the conflict.
- Nobody except the human edits `CONTRACT.md` — not the lead, not any worker. It is only ever changed on `main`.
- If something in the contract is unclear or missing, do not guess. Stop and ask the human.
- Each worktree has its own copy of this file, taken from the skeleton commit. If the contract changes mid-run, the human will tell each affected agent directly in its chat. Treat that message as part of the contract.

## 8. Order of setup (lead)
1. Read this contract fully.
2. Build the skeleton (section 4, "Lead (skeleton)" rows). No feature logic beyond `/health` and the error handler.
3. Start the app and confirm `/health` responds. Show the file tree to the human.
4. Wait for the human's approval. Do not commit before it.
5. Commit `CONTRACT.md`, `CLAUDE.md` and the skeleton to `main`.
6. Only after that commit, create the 5 worktrees exactly as in section 6 — folders next to the project, not inside it.
7. Show `git worktree list` and a table of each agent's folder, branch and `cd` command.

## 9. Rules for every worker
- Work only inside your own worktree folder. Never `cd` into another agent's folder or `main`'s folder.
- Never switch branches. Your folder is already on your branch.
- Edit only the files you own (section 4). Need a change elsewhere (store, `main.py`, `requirements.txt`, another agent's file)? Stop and tell the human what change you need and why.
- Do not add features, fields or endpoints that are not in this contract.
- Before committing, check your own work (run it, call it, or run the relevant tests).
- Commit on your own branch when done, with a clear message. Do not merge, do not push, do not touch `main`.
- Uncommitted work is invisible to the merge. Always commit before reporting done.
- When finished, report: what you built, how you checked it, and every assumption you made.

## 10. Rules for the lead (merging and deploy)
- Work only in the main folder, on `main`. Never edit files inside a worker's folder.
- Before merging a branch, check it has commits: `git log main..<branch> --oneline`. If empty, the worker hasn't committed — tell the human.
- Merge into `main` one branch at a time, in this order: `feat/add-book`, `feat/list`, `feat/tests`, `feat/frontend`, `feat/deploy`.
- Run the full test suite after every merge.
- On a merge conflict or failing test: stop, explain the root cause and which branch it comes from, and use this contract to decide whether the test or the code is wrong. Only change a test if the test contradicts the contract. Propose the smallest fix and wait for the human's approval before applying it.
- After all merges and a green test suite, push `main` only when the human says so. Render deploys from `main`.
